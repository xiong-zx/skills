# 共同汇报方法

## 恢复必要上下文

结合本次问题、最近一次用户决定和项目当前记录核对目标、进展与关键困难。只读取解决本次说明所需的证据；状态文件用于定位，不能代替原始结果。说明别人的工作与自己实际检查的范围，不把收到消息、旧审查或成功运行当成已经完成。

重新接续复杂主题时，先用一两句话说明“现在研究什么、走到哪一步”；补上理解答案必需的定义。正在讨论同一个具体问题时，不反复重述整个项目。沿用稳定的记号、方法名和分类，必要时简短提醒含义，不要求用户回忆旧长回复。

## 筛选后再汇报

默认围绕当前最重要的问题：先给主结论，再给足以判断的依据、关键限制和确需用户决定的事项。目标、进展、证据和下一步是内部检查项，不是每次都要输出的目录。

确需用户决定的事，写成方案一、方案二：各是什么、差别在哪、我的建议，不依赖文档的章节或编号也能读懂；一次只交一两件。研究的基础假设本身就是研究难题，不用按钮或“都按建议吗”催定；先讲清它为什么是这个形式、怎样检验，再谈写法。下一步建议若是大活（派子代理、长推导），写明大致规模。

先让用户有一张小地图。比较多个条件或方案时可以用小表；用户选中或明确追问的部分再深入。详细研究和核查保留在现有材料中，给准确定位，不把全部证明、worker 返回或执行日志复制进回复。简短不得删掉会改变结论的条件或把未知写成已知，也不要用链接替代当前问题所需的答案。

以用户上次已知内容为起点，突出真正新增或改变的判断。用户改变选择时更新当前方向，说明必要的差异；不同时沿用被替代的要求。没有新工作就直说。

## 用具体过程解释

先交代对象、动作和用途，再给必要术语与公式。第一次用到的量就近定义；已有项目记号优先，避免为一次性中间量发明名称。公式只承担本次答案需要的定义、关系或界，随后解释关键项怎样影响结论。需要更多直觉时用一个小例子，而不是增加术语。

正式定理、完整证明和文档排版按对应场景处理；普通进展说明无需自动采用论文的全部展示要求。

## 用批注改进下一次

用户反复问“什么意思”，检查定义、直观例子或推理是否缺失；反复问“现在做到哪”，先恢复目标与位置；说“太多”，重新筛选信息和调整顺序。不要原样重述后再追加更多内容。

处理当次问题后，把已确认的可复用反馈合并到适当的已有规则，保留适用范围，替换冲突旧要求；推测先在会话内试用，含义不明且需要长期采用时集中核对。一次认可只覆盖所评内容，没有批注不表示读过或同意。

交付前检查：用户只读这条消息，能否理解本次答案并作必要判断？若主要内容只是“做了很多事”，重写。衡量汇报是否有效，看它减少了多少理解和决策负担，不看包含了多少结果。
